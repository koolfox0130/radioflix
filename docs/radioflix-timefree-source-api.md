### Read-only wire follow-up (2026-10-21)

**Confirmed by current source:** `config_ini.php` reads `radiko_auth_mode` through `rf_ini_chk(..., default 0, range 0–4)`, and the active `config/rfriends.ini` entry is `0`. The mode-0 route in `rfriends_auth_radiko()` calls `rf_auth()` for its normal path; the premium path is selected separately by `premium_check()` and is not inferred from the mode selector. `rf_auth()` enters `rf_radiko_normal_auth()`. There, `hls_type == 1` selects the auth1/auth2 HLS exchange; otherwise the alternate `rf_radiko_hls()` route is used. The effective `hls_type` and account/premium branch were not disclosed by the safe config scan, so the exact sub-branch currently used is not claimed.

For the auth1/auth2 HLS route, `config_sys_10.php` defines `https://radiko.jp/v2/api/auth1` and `https://radiko.jp/v2/api/auth2` as the `fms1urlhls` / `fms2urlhls` bases. Source builds requests from these values and device headers. The helper invokes wget against those URLs (default GET; no explicit method override was found in these call sites). Auth1 response parsing reads `X-Radiko-AuthToken`, `X-Radiko-KeyOffset`, and `X-Radiko-KeyLength`; the partial key is derived locally. Auth2 receives the device data, token, location and partial key, then parses area information from its response. The code checks wget's process result and parsed response fields; it does not map a uniform HTTP status table. `rf_wget()` additionally requires a nonempty output file. The response is consumed from temporary files/string parsing, rather than a typed HTTP response object.

Mode 2 (not selected by the active selector) constructs `http://<configured-mode2-host>/buddy/auth.php` with `mode`, `pref`, `ver`, and `key=key2` query fields, calls PHP `file_get_contents()` (default GET, no explicit body), and parses a prefixed/encoded body. Its helper tries primary then secondary configured URLs for up to three loop iterations with a one-second pause. Mode 3 (also not selected) performs auth1 then auth2 through the configured FMS endpoints, deriving a partial key from auth1 headers and passing location/token/device data into auth2.

The timefree playlist bases defined by `config_sys_10.php` are `https://radiko.jp/v2/api/ts/playlist.m3u8`, `https://tf-f-rpaa-radiko.smartstream.ne.jp/tf/playlist.m3u8`, and `https://tf-c-rpaa-radiko.smartstream.ne.jp/tf/playlist.m3u8`; code selects among configured globals according to the account/area and tf30 branches. The helper applies configured pre/post margins, formats start/end as `YmdHis`, and builds rectime query fields including `station_id`, `start_at`, `end_at`, `ft`, `l`, and `lsid` (with optional seek/type fields). It writes an input URL list and calls `wget -i ... -O ...m3u8`; the configured m3u8 headers include the auth token, and the tf30 path also supplies the area header. The tf30 helper divides the requested interval into 300-second chunks and combines resolved playlist entries. HLS parsing uses `rf_file_get_contents()` and checks playlist end/time markers before returning stream URLs. ffmpeg later consumes the resulting stream URL in the legacy downloader; this path is not part of Safe Source API.

**Not established:** which of the configured playlist bases is used for the current job/account, effective `hls_type` and premium branch, every request header/body field, all response schemas/status codes, and the full query template after runtime globals are applied. The helpers delegate URL/options to wget or PHP stream wrappers; source shows no common redirect policy, and any redirects/options are delegated to the configured client. No reliable request-local connect/read timeout or HTTP retry matrix was established for the active mode. Mode-2's explicit retry loop does not describe mode 0. No request was executed during this investigation. These findings are source/config observations, not a production wire contract.

Do not treat the fixture routes below as radiko endpoints or a production wire specification.

## Fixture API

`backend/radioflix/timefree/capture/source/` provides `RadikoAuthenticationSource`, `TimefreePlaylistSource`, `HlsMediaSource`, and one `HttpTransport` protocol. The sources construct typed requests; only the transport boundary handles responses. `FakeHttpTransport` consumes in-memory synthetic responses, including auth, timefree playlist JSON, HLS master/media playlists and synthetic segment bytes. No DNS, socket, HTTP library, or external command is used.

The fixture's URL builder uses placeholder paths and JSON response shapes solely to exercise the shared code path. Dummy auth values are plainly marked test data. No captured radiko response or credential is stored.

`HttpRequest` has method, URL, headers, optional body and bounded connect/read timeout. Secret values use `Secret`, whose string and repr are redacted; request/response repr hides headers and body. HTTP method/header validation rejects malformed tokens and CR/LF. Source failures use structured codes and never retain raw exception text.

The URL validator allows HTTPS only, exact hosts `radiko.jp`, `api.radiko.jp`, and `cdn.radiko.jp`, implicit/443 port, no URL userinfo, fragments or literal IPs, and no dot traversal. Playlist URIs are resolved against the already validated base URL and validated again. Redirects are never followed; redirect responses are rejected after validating their Location. Future production transport must also resolve and reject all private/reserved IPs after DNS resolution, but that implementation is absent and cannot run in this fixture.

HLS parsing enforces UTF-8, `#EXTM3U`, URI/tag ordering, unique segments and byte/line/segment limits. The fixture handles a single master variant followed by a media playlist and segment. Multiple variants, key encryption and init maps are rejected. Media is written to a fixed `media-input.ts` filename under the capture workspace through a temporary file, fsync and no-overwrite hard link.

Timeout defaults are connect 3 seconds/read 10 seconds with hard maximums of 15/60 seconds; each source call also consumes the adapter's bounded overall timeout, including HLS playlist and segment requests. Retry is bounded to at most five attempts (default three); only timeout and HTTP 5xx responses retry. 4xx, redirect and parser failures do not. These are RadioFlix fixture policy choices, not claims about rfriends3 behavior. The error model includes `AUTH_FAILED`, `HTTP_TIMEOUT`, `HTTP_REJECTED`, `INVALID_RESPONSE`, `PLAYLIST_INVALID`, `MEDIA_FETCH_FAILED`, and `SOURCE_NOT_READY`.

## Security boundary and next work

No source API accepts a job-supplied URL, command, or output path. The adapter validates job metadata and derives workspace paths; the media source restricts its destination to the configured workspace and fixed filename. Production credentials, HTTP, DNS and HLS are not implemented. Production readiness requires a separately reviewed wire contract for each supported auth mode, DNS/IP pinning or equivalent SSRF defense, redirect policy, bounded stream handling, secret-file integration, egress controls, and error/retry compatibility tests. Until then both write gates remain off and no production deploy or recording trial is eligible.
## Production wire audit (2026-10-23, read-only)

The running container was inspected without invoking PHP helpers, wget, network calls, or any recording function. The active selector output was restricted to non-secret config keys: radiko_auth_mode=0, premium_mode=1, premium_priority=0; no active hls_type INI key was present. Current config_sys_10.php initializes $hls_type=0; source contains only that initialization, normalization, and comparisons. This establishes the normal branch selector as 0 for this source/config snapshot. The current rf_radiko.php, rf_timefree.php, and config_sys_10.php files were fingerprinted read-only; the two capture source files match the pinned manifest.

### Confirmed

- rfriends_auth_radiko(mode=0) with radiko_auth_mode=0 calls rf_auth() and then rf_radiko_normal_auth(). With hls_type=0, this selects rf_radiko_hls() → rf_radiko_hls_sub() → rf_radiko_auth1_hls() then rf_radiko_auth2_hls(). This is the legacy helper path; it still uses auth1/auth2, rather than the separate hls_type==1 implementation.
- Both auth endpoints are source-defined in config_sys_10.php: https://radiko.jp/v2/api/auth1 and /v2/api/auth2. The mode-0 call sites use wget without a method override or request body, so the requests are GET. Auth1 sends X-Radiko-App, X-Radiko-App-Version, X-Radiko-User, X-Radiko-Device, plus pragma; auth2 also sends X-Radiko-AuthToken and X-Radiko-PartialKey. The helper adds a configured User-Agent. Auth1 response parsing requires X-Radiko-AuthToken, X-Radiko-KeyOffset, and X-Radiko-KeyLength; the current hls_type=0 path derives the partial key from playerCommon.js, whose URL is source-defined under https://radiko.jp/apps/js/.
- Auth1 is attempted at most twice by this helper with a one-second delay between attempts. Auth2 has no helper-level retry. Both treat the wget process result as the primary transport success signal; parsed headers/area text then determine semantic success. There is no typed HTTP status mapping.
- The normal timefree helper builds the playlist URL from the primary $playlisturl (https://radiko.jp/v2/api/ts/playlist.m3u8) and rf_radiko_make_rectime(): station_id, start_at + ft, end_at + to, optional seek, l=15, generated lsid, and type=c; the timestamps are YmdHis. It applies timefree_pre_margin / timefree_post_margin (source defaults are zero). Its m3u8header includes --post-data='flash=1', so this wget call is POST with that form body; it also sends auth token, content-type, referer, pragma and disables certificate verification. It writes a temporary URL list, downloads the playlist, then selects the first absolute HTTP URL containing m3u8.
- The conditional tf30 helper divides the adjusted range into 300-second requests. It first queries the source-defined https://radiko.jp/v3/station/stream/pc_html5/ endpoint for stream URL metadata, then chooses a returned playlist base by area-free/timefree attributes. Each slice uses station_id, start_at + ft, end_at + to, preroll, seek, l=300, lsid, and type=b|c; its wget call is GET and includes auth-token and area headers. It combines the returned HLS material and terminates the generated list with #EXT-X-ENDLIST.
- In the inspected rf_common.php, rf_file_get_contents() uses PHP stream wrappers with peer and name verification disabled and no explicit request-local timeout. The timefree helper checks #EXT-X-ENDLIST and, for later slices, #EXT-X-PROGRAM-DATE-TIME. The legacy downloader hands the resulting playlist to its ffmpeg command; it is not a standalone typed segment client.

### Conditional

- premium_check() returns an account/product-dependent branch from product status and the runtime $premium value. premium_mode=1 in the INI is not the $premium branch selector. The effective premium entitlement/state was not inspected because that would require account/session state. The premium helper can use cookie/session and different auth behavior.
- The standard primary playlist path is confirmed from the helper. Whether the job takes the tf30 path and which returned stream URL/base is selected depends on runtime flags and area/account state; those were not resolved from a non-secret selector-only inspection.
- Wget options are assembled from wget_opt / wget_opt_ext, User-Agent and optional proxy globals. The active values were not emitted or copied because they may contain proxy credentials. Their effective timeout/retry/redirect flags therefore remain unverified.

### Unknown and production blockers

- Effective premium branch and per-job standard-vs-tf30 selection.
- Effective wget retry/timeout/redirect flags, proxy configuration, and the complete set of final playlist hosts returned by the stream metadata endpoint.
- Status/body schemas beyond the current parser checks, maximum response sizes, and safe redirect behavior. Wget's client defaults and options determine redirects; rf_file_get_contents() delegates to PHP stream-wrapper defaults. Neither path revalidates redirect hosts.
- Existing auth wget options include --no-check-certificate; the legacy code cannot be copied as a safe TLS policy. No request was made to validate a replacement policy.

These unresolved account/config-dependent details and the legacy TLS/redirect behavior block a production transport design from being safely approved from the available read-only evidence. Block 3 (ProductionHttpTransport) was not started. Production remains NotReady/fail-closed.
